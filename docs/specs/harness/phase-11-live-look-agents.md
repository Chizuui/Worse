# Phase 11: watching the agents, a personal look, more agents

Status: implemented on branch `liquid-glass-ui`. This document says what each addition does, which code owns
it, what it stores, what it costs, and how far it was verified. Section 9 lists what was *not* verified.

## 1. Goals

1. Show what an agent is doing while it does it: the code it reads and edits, the computer it uses, the
   subagents it started.
2. Let the user choose the look: the "thinking" animation, the unicode field, a wallpaper.
3. Run two more agents out of the box: Command Code (with several API keys) and Hermes (through its gateway).

Not goals: replaying keystrokes of an edit (agents send an edit as one old/new pair), video wallpapers, a name
tag on the real desktop pointer (section 5.4).

## 2. Live code view

**What the user sees.** A tool row carries a chip with the lines it covered (`L40–96`; `+2 −1` when the agent
gave no line). A collapsed edit row shows its first six changed lines. The side pane has a **Live** tab: the file
the agent is reading or editing, a window of 80 lines before and 200 after the touched lines, those lines
marked (lime = read, amber = about to change, green = written), a trail of the files of the turn, and a
Follow / Pause button. Clicking a chip or the diff peek opens the file there and pauses following; scrolling
the code pauses it too.

**Owner.** `apps/harness-slint/src/live.rs` (targets, file window, highlighting), `ui/panels/live.slint`
(`LiveUi`, `LivePanel`), `ui/chat/turns.slint` (`ToolCard` chip and peek), `src/bridge/turns.rs` (`peek_parts`,
row facts).

**Rules.**
- A tool row gets its file and range from the tool call alone (numbered read output, diff content,
  locations); no file is read for it, so loading a long session stays cheap.
- The file is read from disk only while the Live tab is on screen (`LiveUi.active`). Files over 4 MiB are not
  shown.
- A read reports twice (started, finished) with the same span; the view is rendered once.
- Long lines are not wrapped: the row is as wide as the longest line and the list scrolls sideways.

## 3. Look

All of it lives in the `Look` global (`ui/theme/look.slint`), filled from `settings.json` by
`src/settings/mod.rs` and `src/wallpaper.rs`.

### 3.1 Thinking animations

`appearance.thinkingStyle`: `scan` (default, the previous animation) | `bars` | `pulse` | `quads` | `charge` |
`moon` | `cipher` | `chevrons` | `bunny` | `shuffle` (a different one every turn). `appearance.statusWords`:
`plain` | `playful`.

Frames are generated by `scripts/ui/gen-ascii-art.mjs` into `ui/brand/ascii_art.slint` (`AsciiArt.think`) and
use only glyphs of the bundled mono face. `ThinkGlyph` (`ui/components/ascii.slint`) shows one in a box of
fixed size and steps on the shared busy clock (90 ms). Settings previews run on their own timers.

### 3.2 Unicode field

`appearance.backdropField`: `dither` (default) | `rain` | `stars` | `circuit` | `none`.
`appearance.backdropMotion`: `home` (moves on the empty chat only, default) | `always` | `off`.

`rain` and `circuit` repeat every 36 rows (two 18-row bands stacked alternately); `stars` has six different
bands like `dither`. Without a wallpaper the drawing of `dither` is unchanged (compared pixel by pixel with the
previous build). Over a wallpaper the field fades through a gradient in its own ink instead of painting the
canvas over itself.

### 3.3 Wallpaper

`appearance.wallpaperPath` (PNG, JPEG, BMP, WebP, animated GIF or WebP; empty = none),
`appearance.wallpaperBlur` (0–40, pixels of a 1440 px wide window), `appearance.wallpaperDim` (0–95 %).

- `src/wallpaper.rs` decodes, scales and blurs on a worker thread; the UI thread swaps finished pixel buffers.
  A still is kept at most 1920 px wide (smaller when blurred). The dim is a veil of the canvas colour drawn by
  Slint, so the slider answers at once and follows the theme.
- Glass panels (`Frost` in `ui/theme/backdrop.slint`) show a 192 px wide, heavily blurred copy of the
  wallpaper, placed where the window shows the wallpaper. That is how they look frosted without a
  backdrop-blur pass, which Slint does not have.
- An animation is decoded smaller until all frames fit 48 MB, at most 400 frames. The clock picks the frame,
  so a slow repaint skips frames instead of slowing the animation down. On the CPU renderer at most 10 frames
  a second are shown (20 on the GPU). Over an animation the panels use a flat veil instead of the frosted
  copy. It is paused while the window is hidden, not focused, or reduced motion is on.

### 3.4 GPU rendering

`general.gpuRendering` (default off) replaces `general.hardwareAcceleration`, which was never read. On, the
window is drawn by GPU Skia after a restart. The renderer is chosen before the settings store exists, so
`select_renderer` (`src/main.rs`) reads the value from `settings.json` directly. `HARNESS_RENDERER=cpu|gpu`
overrides it.

### 3.5 Decoration rests when unfocused

`ArtClock.focused` follows the window focus. Hero art, the unicode field and an animated wallpaper rest
without it. The pieces that show an agent at work (thinking line, tool spinners, team strip) keep going.
A focused or hovered window also counts as visible: X11 without a window manager reports the window as
occluded at startup.

### 3.6 Rounded window on Windows 11

With the custom title bar ("Use Windows title bar" off) the window is frameless, and Windows 11 draws a
frameless window square and without a shadow. `apps/harness-slint/src/window_frame.rs` asks DWM for the normal
look through winit's window attributes: `CornerPreference::Round` (DWM rounds and anti-aliases the corners,
and squares them again while the window is maximized or snapped) and the undecorated shadow. The frame follows
the app's theme (`set_theme` on the winit window), so the thin border DWM draws is dark in the dark theme; this
does not touch winit's record of the system theme that Slint reads for "System". The radius is DWM's own
(8 px), not configurable. Windows 10 has no corner preference and stays square. With the Windows title bar on,
Windows 11 rounds the window by itself.

## 4. Team strip

A session that delegated work shows, above the composer, one lane per subagent that is still working: agent,
the step in progress, the three steps before it, the step count, the elapsed time, and "needs approval" when
it waits. Clicking a lane opens the subagent's session; Stop appears on hover; "Orchestra" opens the live
canvas. At most four lanes are shown; the rest are counted.

The core reports only a subagent's current activity (`SubagentView.activity`). The UI keeps the trail itself
(`Trail` in `src/bridge/turns.rs`); it is lost when the app restarts.

### 4.1 Generation speed

`appearance.showTokenSpeed` (default on). `src/speed.rs`.

- While the agent writes, the working line shows an estimate: characters received ÷ 4, over the time text
  was actually arriving ("≈ 96 tok/s"). No agent reports token counts in the middle of a turn. The figure is
  removed when no text arrived for two seconds.
- After the turn, the answer row carries the turn's figure. When the agent reported the output tokens of the
  prompt (`TurnView.usage`, from the ACP `session/prompt` result) it shows those tokens over the model's
  working time ("89 tok/s · 280 output tokens"); otherwise the estimate stays, marked "≈".
- The model's working time is the turn's wall time minus the time at least one tool row was running or
  waiting for an approval. The reported count covers every model call of the turn, including thinking and
  tool call arguments that never stream as answer text, so dividing it by the time answer text arrived gave
  impossible rates (2026-11-18: 9303 tokens over about 1.2 s of text, "7613 tok/s", in a 325 s turn with 103
  tool calls). Hermes pairs the same two quantities per API call (output tokens over call duration); an ACP
  agent reports one total per prompt, so the turn is the unit here.
- For the live estimate only time during which text arrives counts: a gap of more than two seconds is a tool
  or an approval, not generation.

## 5. Computer use, live

### 5.1 What the user sees

In Machine mode the Live tab offers **Code | Screen**. Screen shows the agent's last screenshot, its pointer
in the agent's colour with the agent's name on a tag, a ripple where it clicked, a bubble with what it typed,
pressed or scrolled, and the last actions. With follow on, the tab switches to whichever the agent used last
and comes to the front once per turn when the agent starts using the computer.

### 5.2 How it gets there

The `harness-computer` MCP server (`src/computer_mcp.rs`) runs in the agent's process tree. Before each action
it appends one JSON line to `<home>/machine-live/<session>/events.jsonl`:

```json
{"seq":3,"t":1794914912323,"kind":"click","text":"left at 520, 420","w":1440,"h":900,"x":520.0,"y":420.0}
```

`kind`: `screenshot`, `move`, `click`, `double`, `right`, `drag`, `drop`, `scroll`, `type`, `key`. `x`, `y`
are pixels of the last screenshot (`w` × `h`). After a screenshot it writes `screen.jpg` (at most 1280 px wide,
written whole and renamed). The log starts over past 512 KiB. Failing to write never fails the tool.

`src/machine_view.rs` reads both on a 150 ms timer, only while the open session has Machine mode on, and fills
`ScreenUi` (`ui/panels/screen.slint`). The directory is removed at startup: screenshots of the screen do not
outlive the app.

### 5.3 The real pointer

`glide` moves the pointer along an eased path (120 ms for a short hop, 360 ms across the screen, a step about
every 16 ms) before a click, move, drag or scroll. `HARNESS_MACHINE_GLIDE=0` restores the jump.

### 5.4 Not included: a name tag on the desktop

A tag that follows the real pointer needs a transparent, click-through, always-on-top window that never takes
the focus from the application the agent is driving. If it took the focus, the agent's keystrokes would go to
the tag. That behaviour differs per window system and cannot be checked without one, so it was left out.

## 6. Hermes through its gateway

Add it under Settings → Agents → API providers (preset "Hermes gateway": `http://127.0.0.1:8642/v1`, model
`hermes-agent`, key = the gateway's `API_SERVER_KEY`).

`crates/harness-api-agent/src/hermes.rs`. A gateway is a whole agent that runs its own tools on its host, so
for it the API agent does not run its tool loop and sends no tools:

| Hermes sends | Harness shows |
| --- | --- |
| `data:` chunk with `delta.content` | answer text |
| `data:` chunk with `delta.reasoning_content` | thinking |
| `event: hermes.tool.progress` `{tool, label, toolCallId, status}` | a tool row that starts and completes |
| `event: hermes.status` `{kind, text}` | a line of thinking |
| `event: approval.request` `{run_id, command, description, choices}` | a permission request; the answer goes to `POST /v1/runs/{run_id}/approval {"choice": …}` |

The request carries only the new message (plus one `system` line with the project directory) and
`X-Hermes-Session-Id: harness-<session>`; the conversation lives in Hermes. Closing the stream cancels the
run. Harness's modes are not offered for a gateway. The endpoint is recognised by
`GET {base}/capabilities` (`"object": "hermes.api_server.capabilities"`), remembered per endpoint in the
provider's state directory; `HARNESS_PROVIDER_KIND=hermes|openai` overrides.

Other agents can delegate to Hermes through `harness-delegate` like to any agent. Hermes cannot delegate back:
it does not load Harness's MCP servers.

## 7. Command Code and key pools

- **Built in.** Agent `command-code` runs `command-code acp` (the CLI's own ACP mode). The npm package also
  installs `cmd`; that is the Windows shell's name, so the long name is used.
- **Keys.** A `providers.json` entry of kind `command-code` is one API key. It becomes agent
  `command-code-<name>` ("Command Code · <name>") that runs the CLI with `COMMAND_CODE_API_KEY`. The dialog's
  "Command Code CLI" preset takes one key per line.
- **Without the CLI.** Command Code also serves an OpenAI-compatible Provider API,
  `https://api.commandcode.ai/provider/v1` (Bearer key, the same key as the CLI; every plan except Go;
  https://commandcode.ai/docs/provider). The "Command Code API" preset makes it a plain API provider for
  Harness's own agent. Claude models answer only on its `/messages` route, so they are not available there;
  the default model is `deepseek/deepseek-v4-flash`.
- **Key pools** (`crates/harness-agent-hub/src/providers.rs`, `HubCtx::rotated`). All Command Code keys form a
  pool; so do providers that share endpoint and model. A new session asked for a pool member, or for the
  built-in Command Code agent, gets the pool's next member that is installed and not at its usage limit. This
  covers delegated subagents, so parallel subagents use different keys. An explicit choice of agent for a
  turn in an existing session is not rotated.
- **Limits.** A usage limit mid-turn fails over to the next agent in the fallback order, where the keys sit
  next to each other; the rotation skips an exhausted key until it resets.
- **Off switch.** `"rotation": "off"` in `providers.json`, or `HARNESS_KEY_ROTATION=off`.
- **Saving several keys.** The dialog sends one add per key and each runs in its own task. Every
  read-modify-write of `providers.json` now holds one lock (`providers::WRITE`); before, concurrent adds read
  the same file and only one of them survived, so a paste of several keys could keep just one.

## 7a. Provider presets

`Add provider` opens on a grid of providers (`apps/harness-slint/src/settings/presets.rs`). Picking one fills
the name, the endpoint and a default model; the user pastes a key ("Get a key ↗" opens the provider's key
page) and saves. The endpoint stays editable ("Edit"), and "Several keys" takes one key per line, saved as
numbered providers with the same endpoint and model, which makes them a round-robin pool.

- **Presets.** Command Code API, OpenRouter, OpenAI, DeepSeek, Gemini (its OpenAI-compatible endpoint), xAI,
  Mistral, Groq, Kimi, Z.ai GLM, Qwen (Model Studio international), MiniMax, Together, Fireworks, Cerebras,
  NVIDIA NIM, Hugging Face, Vercel AI Gateway, OpenCode Zen, Ollama and LM Studio (local, no key), the Hermes
  gateway, the Command Code CLI keys, and "Other endpoint". Endpoints follow each provider's documentation and
  the provider tables of hermes-agent (`hermes_cli/auth.py`) and oh-my-pi
  (`packages/catalog/src/provider-models/openai-compat.ts`). Providers whose main API is not Chat Completions
  for Harness's purposes (Anthropic, Nous Portal with its OAuth-only login) are left out.
- **Models.** Model ids change often, so a default is only filled where the documentation names a current
  one; elsewhere the field is empty. "List models" asks the endpoint (`GET <endpoint>/models` with the first
  key) and shows its ids; typing filters them, a click picks one. A local preset lists its models as soon as it
  is picked. OpenAI's `{"data": [{"id"}]}`, Ollama's `{"models": [{"name"}]}` and a bare list are read.
- **Marks.** Each preset shows its provider's mark (LobeHub Icons, `ui/icons/LICENSES.md`); the mark is found
  from the provider's name or id, so it also shows in the provider list, the agent picker and the session list.
  A name without a mark ("Other endpoint", a provider named by the user) shows its first letter in the dialog.

## 8. Measurements

Release build, software-rendered X server, window 1440×900, one core = 100 %. Measured with the art actually
running (window focused and visible).

| State | CPU | Memory (RSS) |
| --- | --- | --- |
| Home, reduced motion (nothing moves) | 0.0 % | 74 MB |
| Home, hero art running (dither field) | 4.8 % | 75 MB |
| Home, window not focused (the art rests) | 0.1 % | 75 MB |
| Home, rain field | 10.5 % | 75 MB |
| Home, still wallpaper, blur 8 | 6.4 % | 81 MB |
| Home, animated GIF wallpaper (480×270, 24 frames) | 34.6 % | 94 MB |
| The same, window not focused | 0.1 % | 93 MB |
| A turn running, side pane on Overview | 8.5 % | 79 MB |
| A turn running, Live tab following the agent | 14.2 % | 83 MB |
| Chat idle after the turn | 0.5 % | 80 MB |

Before the frame cap and the flat veil (section 3.3) the same GIF took 50 %. A GIF wallpaper is still the one
costly choice on the CPU renderer; GPU rendering (section 3.4) is the answer for it, and was not measured
(no GPU here).

An earlier idle figure of about 1 % CPU for the animated home screen was taken while the art was paused by the
occlusion check (section 3.5), so it described the paused state, not the animated one.

## 9. Verification, and what was not verified

Verified by running the real app under a virtual X server:

- Live code view with an agent that reads line ranges and makes real edits on disk: chips, diff peek, the
  Live tab following, opening from a chip, long lines.
- Wallpaper (JPEG still, animated GIF), the four unicode fields, the settings page.
- Team strip with the fake core's demo subagents.
- Computer use end to end: Machine mode switched on in the UI, the real `--computer-mcp` helper taking
  screenshots and moving, clicking, scrolling and typing; the Screen view; the pointer glide (sampled).
- Hermes against a stand-in gateway that follows the frame shapes of hermes-agent's `api_server` (HEAD
  43dc9a0a): detection, two turns in one session, tool rows, each approval choice, deny, cancel, wrong key,
  gateway down, and the flow in the app.
- Command Code: the real CLI (1.89.2) answers ACP `initialize` and refuses `session/new` without a login. With
  a stand-in CLI: rotation over three keys, failover at a usage limit, rotation off.
- Generation speed with an agent that streams at a steady pace: the live estimate, the exact figure when the
  agent reports tokens, the estimate when it does not, and nothing with the setting off.
- Unit tests: `live::`, `wallpaper::`, `machine_view::`, `computer_mcp::`, `speed::`, `bridge::turns::`,
  `settings::presets::`, `harness-api-agent hermes::`, `harness-agent-hub providers::` (six concurrent adds
  keep all six entries; the same test fails without the lock).
- Provider presets in the app, against a stand-in server on LM Studio's port: the grid, picking LM Studio
  (models listed without a key), picking a model, two keys saved as "LM Studio 1" and "LM Studio 2", "List
  models" sending the first key, the Command Code API preset's filled form.
- The Windows build: cross-compiled from Linux (`cargo xwin build --release --target x86_64-pc-windows-msvc
  -p harness-slint --bins`; cargo-xwin 0.23.1 with clang-cl and lld-link 18) and run under Wine 9.0 with CPU
  rendering: start through the shadow copy, the Appearance and Agents pages, a wallpaper picked in the Windows
  file dialog, and one turn against the stand-in Hermes gateway (the app's own `--api-agent` process, tool
  rows, an approval, the tok/s label).

Not verified:

- Real Windows, and anything on macOS. The Windows build ran under Wine only (above); the Linux runs were
  under Xvfb with CPU rendering.
- GPU rendering (`general.gpuRendering`), Direct3D on Windows included: the switch selects the renderer that
  was the default before; no GPU was available to run it.
- A real Hermes gateway and a real Command Code key (`COMMAND_CODE_API_KEY` in ACP mode follows the CLI's
  documentation of its headless login), and any real provider behind a preset: no key was sent to a provider.
  Default model ids come from documentation and may be renamed; "List models" shows what an endpoint serves.
- Rounded corners on Windows 11 (section 3.6): Wine has no DWM, so the corner preference and the frame theme
  were only type-checked for the Windows target.
- The wallpaper file picker on Linux (GTK). The Windows dialog was driven under Wine; the settings write behind
  both is the same one the tests use.
- New interface strings are English only; the Chinese translation falls back to English for them.

Found on the way, in a dependency and not changed here: the frame throttle of Slint 1.18.1
(`i-slint-backend-winit`, `frame_throttle.rs`) divides by the monitor's refresh rate. A display that reports
0 Hz makes the app panic at its first redraw. Wine on Xvfb reports 0 Hz and hit it; a Wine virtual desktop
reports 60 Hz and runs. Windows documents 0 and 1 as "hardware default" values of `dmDisplayFrequency`, so a
real display can report them too.
